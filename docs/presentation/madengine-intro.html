The problem

The same model, five different ways to run it

A benchmark that works on a workstation rarely survives a move to a cluster. Image names, launchers, schedulers and result formats all change, and the number you report stops meaning the same thing.

01docker run by hand: device flags, mounts, environment
02sbatch scripts per cluster: modules, srun fan-out, rank variables
03Kubernetes manifests Jobs, PVCs, secrets, GPU resource names
04Serving stacks helm releases and gateways, as with llm-d
05Result formats every harness prints something different

With madengine: one model card, one flag changes

bash
# local Docker
madengine run --tags pyt_vllm_llama-3.1-8b_fp8

# SLURM: add a slurm block
madengine run --tags pyt_vllm_llama-3.1-8b_fp8 \
  --additional-context '{"slurm": {"partition": "gpu"}}'

# Kubernetes: add a k8s block
madengine run --tags pyt_vllm_llama-3.1-8b_fp8 \
  --additional-context '{"k8s": {"gpu_count": 1}}'

# llm-d: add an llm_d block
madengine run --tags pyt_vllm_qwen3-32b \
  --additional-context-file \
    examples/llm-d-configs/01-attach-existing-stack.json
Same model card. Same perf.csv. The context decides where it runs, and no code changes between targets.

Quick start

Four commands to a first number

Install madengine, clone MAD, find a model, run it. The container, the log scan and the result row come with it.

bash · from your MAD checkout
pip install git+https://github.com/ROCm/madengine.git
git clone https://github.com/ROCm/MAD.git && cd MAD

madengine discover --tags pyt_vllm_llama-3.1-8b_fp8

export MAD_SECRETS_HFTOKEN="<your Hugging Face token>"
madengine run --tags pyt_vllm_llama-3.1-8b_fp8 \
  --keep-model-dir --live-output

What happens

  1. Discover finds the card by name or tag in the catalog.
  2. Build makes the image from the card's Dockerfile. For a build, gpu_vendor defaults to AMD and guest_os to UBUNTU.
  3. Run starts a container named container_ci-pyt_vllm_llama-3.1-8b_fp8, with a watchdog as PID 1.
  4. Results land in perf.csv. This card also leaves perf_Llama-3.1-8B-Instruct-FP8-KV.csv. Failed runs are recorded as FAILURE, so every attempt appears.
Prerequisites: Docker, Python 3.9+, and ROCm or CUDA drivers. If ROCm is not auto-detected, set MAD_ROCM_PATH.

--live-output streams logs. --verbose adds detail. --timeout 0 disables the timeout, -1 defers to the card.

--keep-alive leaves the container up. --skip-model-run runs only setup and pre-scripts, so you can docker exec in.

The pipeline

Build once, run anywhere

Build and run can be separate steps. The manifest carries the image and the Context that built it, so the same artifact runs on a workstation, a SLURM login node, or a cluster that only pulls from a registry.

bash · split workflow
# CI or laptop: build and push
madengine build --tags pyt_vllm_llama-3.3-70b \
  --registry docker.io/myorg

# any target: run from the manifest
madengine run --manifest-file build_manifest.json
  • Pre-built images: --use-image <ref> or MAD_CONTAINER_IMAGE skips the build entirely.
  • Build on compute: --build-on-compute --registry … builds inside a SLURM job and pushes.
  • Pinned digests: every push records image_digest. --require-pinned-image pulls repo@sha256:… and fails instead of running a moved tag.

The Context 3.0 preview

One Context drives everything

Every setting for an invocation lives in one dictionary. It is merged from several sources and stored with the images, so build and run agree.

Host facts
GPU vendor and architecture, OS, ROCm path, detected at start
Inline
--additional-context '{…}': JSON first, then a Python literal
File
--additional-context-file. File and inline are deep-merged, inline wins key by key
YAML
--config: Hydra groups plus a user file. Mutually exclusive with the two above
Presets
Minimal K8s, SLURM and llm-d configs are merged with JSON presets automatically
YAML priority, highest first: inline overrides › user YAML › config groups › base defaults.

Convention over configuration

The target is inferred from the keys you wrote

There is no deploy flag to set. The first rule that matches wins, so the order matters.

Why this is nice

  • Moving a job between clusters is a diff of one block, not a new script.
  • Conflicting blocks are rejected at validation, for example slurm together with k8s.
  • Unknown top-level keys are reported, which catches typos like slrum.
Bare metal cannot be combined with slurm, k8s, kubernetes or llm_d. See docs/bare-metal.md.

Local

ContainerRunner

docker run with GPUs, mounts, env, a PID 1 watchdog and tool wrappers. BareMetalRunner does the same in a conda prefix.

SLURM · Spur

SlurmDeployment

Renders an sbatch script. SpurDeployment subclasses it and swaps srun fan-out for a job array with a shared-filesystem rendezvous.

Kubernetes

KubernetesDeployment

Job or Indexed Job, a headless Service for multi-node, ConfigMap with scripts, optional PVCs and secrets.

llm-d

LlmdDeployment

Subclasses Kubernetes: the benchmark client is an ordinary one-pod Job. LlmdStack drives helm in managed mode.

Presets live in deployment/presets/ and are merged with a minimal user config by config_loader.py, so {"k8s": {"gpu_count": 2}} is a complete configuration.

Lifecycle and reliability

A cancelled run should not hold your GPU

CI runners kill the step's shell and nothing else. Containers started with docker run -d used to survive that and pin the GPU until a reboot. Three layers now cover it.

Layer 1 · survives SIGKILL

In-container watchdog

PID 1 is a POSIX-shell watchdog. It stops the container when its heartbeat file in the bind-mounted workspace goes stale. Tune with MADENGINE_HEARTBEAT_INTERVAL (15 s) and MADENGINE_HEARTBEAT_STALE_AFTER (120 s).

Layer 2 · SIGINT · SIGTERM · SIGHUP

Signal handlers

Drop the heartbeats, tear down registered containers within a 6 s budget, exit 130. A cancel also deletes a submitted SLURM or Kubernetes job and uninstalls a managed llm-d stack.

Layer 3 · after the fact

madengine cleanup

Sweeps containers whose owning process is gone. Safe from if: always() or cron. --dry-run reports only, --all ignores ownership.

Exit codes for CI

0SUCCESS3RUN_FAILURE
1FAILURE4INVALID_ARGS
2BUILD_FAILURE5GPU_WEDGED (cleanup)
A wedged GPU is claimed only on evidence. D-state PIDs, or a container the daemon still lists after two removals. Then gpu_wedged.json is written and cleanup exits 5, so CI can pull the runner out of rotation.

Launchers

Three launcher contracts, ten names

A launcher is how a workload starts inside its own container, not the scheduler or the platform. Validation rejects a launcher on a target with no arm for it.

Contract 1

Templated

torchrun deepspeed megatron-lm torchtitan vllm sglang sglang-disagg vllm-disagg. The deployment templates render the start command.

Contract 2

Self-managed

slurm_multi. The card's own .slurm script starts its containers. Used by MAD's disaggregated and communication benchmarks.

Contract 3

Primus

primus. A local single-node run. The model script starts Primus. A cluster block is rejected.

Results

One schema for every target

Each run appends rows to perf.csv. A card that names multiple_results appends one row per row of that file, so a concurrency sweep becomes a table.

  • Failures are rows. Pre-run and run failures are written with status FAILURE.
  • Stale files are removed. A normal run deletes a leftover multiple_results file first, so an appending script cannot report the previous run.
  • llm-d rows record the serving stack: deployment_type=llm-d, launcher vllm or vllm-disagg, and serving_mode.
  • Bare-metal rows record platform=bare_metal and deployment_type=local.
bash · after the run
madengine report to-html  --csv-file-path perf_entry.csv
madengine report to-email --directory ./results
madengine database --file perf_entry.csv \
  --db mydb --collection results

Example 1 · local Docker · 1 GPU

vLLM on Llama 3.1 8B, FP8

A model card is a few fields. madengine supplies the container, the environment and the result collection around it.

scripts/vllm/models.json · pyt_vllm_llama-3.1-8b (abridged)
{
  "name": "pyt_vllm_llama-3.1-8b",
  "dockerfile": "../../docker/pyt_vllm",
  "scripts": "run.sh",
  "data": "huggingface",
  "n_gpus": "-1",
  "multiple_results": "perf_Llama-3.1-8B-Instruct.csv",
  "tags": ["pyt", "vllm", "vllm_extended", "inference"],
  "timeout": -1,
  "args": "--model_repo meta-llama/Llama-3.1-8B-Instruct --config configs/extended.yaml"
}

The FP8 card differs only in --model_repo amd/Llama-3.1-8B-Instruct-FP8-KV and its CSV name. n_gpus: "-1" means every visible GPU.

Run it

bash
export MAD_SECRETS_HFTOKEN="<token for gated models>"

madengine run --tags pyt_vllm_llama-3.1-8b_fp8 \
  --keep-model-dir --live-output

What you can check afterwards

  • Container container_ci-pyt_vllm_llama-3.1-8b_fp8 ran with a watchdog as PID 1.
  • perf_Llama-3.1-8B-Instruct-FP8-KV.csv holds the sweep. perf.csv has one row per line of it, merged with image, GPU architecture and status.
  • MAD_SECRETS_HFTOKEN is mapped to HF_TOKEN inside the container.
  • --keep-model-dir keeps downloaded weights, so the second run starts fast.
Same card, same CSV, on any target. The next examples only change the Context.
Example 2 · local Docker · 8 GPUs

Kimi-K3 at TP8, three engines

A 2.8T-parameter model on 8× MI350X or MI355X. One tag per framework, the same command shape.

bash
# vLLM, SGLang and ATOM on the same hardware
madengine run --tags pyt_vllm_kimi-k3   --keep-model-dir --live-output
madengine run --tags pyt_sglang_kimi-k3 --keep-model-dir --live-output
madengine run --tags pyt_atom_kimi-k3   --keep-model-dir --live-output

# the checkpoint is about 1.56 TB: reuse weights you already have
madengine run --tags pyt_vllm_kimi-k3 --keep-model-dir --live-output \
  --additional-context '{
    "docker_mounts":   {"/model_weights": "/path/to/Kimi-K3"},
    "docker_env_vars": {"MAD_DATAHOME": "/model_weights"}
  }'

Each tag brings its own image and config: vLLM configs/default.yaml, SGLang configs/kimi_k3.yaml, ATOM configs/default.yaml.

Pick the GPUs, or run a diffusion model that needs all eight

bash · xDiT, n_gpus: 8
MAD_SECRETS_HFTOKEN=hf_xxx \
  madengine run --tags pyt_xdit_flux --live-output
# latencies land in results.csv (multiple_results)

# restrict a local run to a subset of GPUs and CPUs
madengine run --tags pyt_vllm_llama-3.3-70b \
  --additional-context '{
    "docker_gpus": "0,1,2,3",
    "docker_cpus": "0-31"
  }'
  • docker_gpus takes a list with ranges, like "0,2-4,7".
  • MAD ships 14 xDiT cards: FLUX.1, FLUX.2, Wan 2.1 and 2.2, HunyuanVideo, Qwen-Image, SD 3.5 and more. All use n_gpus: 8.
  • On a shared host add --wait-for-gpu-memory 60 so a neighbour's job does not skew the run.
Example 3 · local Docker · training

Primus pretraining on one node

Llama 3.1 8B in BF16 on MI300X, through Megatron or TorchTitan. Primus configs are discovered from the Primus submodule, so the tag encodes backend, GPU and config. Backends: megatron, torchtitan, megatron_bridge, nemo_automodel, diffusion, moe_package. GPUs: MI300X, MI325X, MI355X, MI455X.

bash
cd /path/to/MAD
git submodule update --init --recursive scripts/Primus   # first time only

# tag = primus_train/<backend>_<GPU_ARCH>_<MODEL_CONFIG>
madengine build --tags primus_train/megatron_MI300X_llama3.1_8B-BF16-pretrain
madengine run   --tags primus_train/megatron_MI300X_llama3.1_8B-BF16-pretrain \
  --live-output

# same config on TorchTitan
madengine run --tags primus_train/torchtitan_MI300X_llama3.1_8B-BF16-pretrain \
  --live-output

madengine discover --tags primus      # all 399 Primus cards
madengine discover --tags torchtitan  # one backend
madengine discover --tags MI300X      # one GPU

Override the environment without editing the card

bash
madengine run \
  --tags primus_train/megatron_MI300X_llama3.1_8B-BF16-pretrain \
  --live-output \
  --additional-context '{"docker_env_vars": {
    "MAD_SECRETS_HFTOKEN": "<token>",
    "HSA_NO_SCRATCH_RECLAIM": "1"
  }}'
  • MAD_SECRETS_HFTOKEN is needed only with real data. The default configs use mock data.
  • On the local Docker path a card's own env block is not read. Use docker_env_vars.
  • The image is rocm/primus, set by BASE_DOCKER in docker/primus.ubuntu.amd.Dockerfile. Each card runs 8 GPUs with a 24-hour timeout.
  • JAX MaxText and MaxDiffusion have their own cards and image. See the next slide. The six pyt_train_* cards (Flux, SDXL, DLRM, Mochi, Hunyuan, Wan) use docker/pytorch_train.
Primus is a local single-node launcher. Adding a slurm or k8s block to a primus run is rejected at validation. For multi-node training, use a templated launcher.
Example 3b · local Docker · JAX training

JAX MaxText and MaxDiffusion on one node

Both run through Primus on a JAX image. One card is generated per Primus YAML, so new configs appear without a MAD change.

bash · from your MAD checkout
# Primus must exist at scripts/Primus before discovery
bash tools/fetch_primus.sh
export MAD_SECRETS_HFTOKEN="<your Hugging Face token>"

madengine discover --tags jax         # MaxText + MaxDiffusion

Launchers and parallel strategies

What each launcher actually parallelizes, the settings that matter, and the practices that keep multi-node runs boring.

Training

Training launchers and their parallel strategies

DDP and FSDP, the default workhorse

  • Use when: small to medium PyTorch models, standard data-parallel patterns.
  • Parallelism: data parallel (DDP) and FSDP, both set up in your script. No built-in TP or PP.
  • Gives you: automatic rank assignment, NCCL, elastic training support.
  • Master port: distributed.port or master_port, default 29500. On SLURM port wins if both are set.
Practice: keep nproc_per_node equal to GPUs per node, and k8s.gpu_count equal to it.
json
{
  "distributed": {
    "launcher": "torchrun",
    "nnodes": 2,
    "nproc_per_node": 8,
    "port": 29500
  }
}
bash · in the model script
$MAD_MULTI_NODE_RUNNER train.py ...
# → torchrun --nnodes=2 --nproc_per_node=8 ... train.py

ZeRO when the model does not fit

  • Use when: models that exceed a single GPU's memory, ZeRO-1/2/3, gradient accumulation, mixed precision.
  • Parallelism: data parallel with ZeRO partitioning (auto). Pipeline and tensor degrees are manual.
  • How: its own launcher, not torchrun. madengine writes a hostfile: one per SLURM job, and in place inside salloc with a unique suffix.
  • Needs: a DeepSpeed config file referenced by your model script.
Practice: plan for about 32 GB per GPU with ZeRO-3.
json
{
  "distributed": {
    "launcher": "deepspeed",
    "nnodes": 4,
    "nproc_per_node": 8
  }
}

  --hostfile=/tmp/deepspeed_hostfile_${SLURM_JOB_ID}.txt ..."

Tensor inside a node, pipeline across nodes

  • Use when: GPT, BERT, T5-style transformers, 70B and up.
  • Parallelism: TP, PP and CP configured automatically. DP is implicit.
  • Single node: TP only, PP = 1. Multi-node: TP across the GPUs of a node, PP across nodes.
  • Built on: torchrun, so MAD_MULTI_NODE_RUNNER applies.
Practice: keep tensor parallel within the fastest interconnect, which is inside the node, and let pipeline stages cross the network.

Inference

Inference launchers and how they scale

Tensor parallel in a node, replicas across nodes

  • Single node: TP across the GPUs, no Ray.
  • Kubernetes, multi-node: data parallel, independent replicas per pod.
  • SLURM, multi-node: data parallel, one vllm serve per node, TP only inside that node, no shared Ray cluster.
  • Faster startup, easier failure: nodes are independent, so one bad node does not stall the rest.
Practice: for MoE and very large dense models, use a card or a disaggregated setup that sets expert parallelism, because the launcher itself only sets TP and replicas.

VLLM_DISTRIBUTED_BACKEND="auto"   # "none" for SLURM multi-node DP

RadixAttention and structured generation

  • Native launcher: sglang.launch_server, no torchrun.
  • Prefix caching: RadixAttention reuses shared prefixes, which helps agentic and multi-turn traffic.
  • Parallelism: TP automatic. Multi-node uses native support with Ray. DP is limited.
  • Structured generation is a first-class feature.

Separate the prompt phase from the token phase

  • Roles: a proxy, xP prefill nodes that build the KV cache, and yD decode nodes that generate tokens.
  • Why: prefill is compute-bound and decode is memory-bound, so each pool can be sized and tuned on its own.
  • Names: sglang-disagg (Mooncake) and vllm-disagg 3.0. Cluster only: min 2 nodes on SLURM and Spur, 3 on Kubernetes.
  • MAD's cards (MoRI IO, Mooncake, NIXL, DeepEP) run through slurm_multi with xP and yD in env_vars.

The escape hatch for topologies the templates cannot express

  • What: the card's own .slurm script runs on the head node and starts per-node containers itself with srun.
  • madengine adds: a wrapper sbatch that exports the card's env_vars, parallel docker pull on all nodes, and a completion marker.
  • Inside salloc: runs synchronously with bash instead of nesting another sbatch.
  • Targets: SLURM, Spur and Kubernetes. Not llm-d.
  • Not a peer of the templated launchers. Use those for standard workloads.

Best practice · disaggregated serving

Sizing prefill and decode

The automatic split gives prefill about 40% of the worker nodes and decode about 60%, after setting aside one proxy node. Treat it as a starting point and tune from measurements.

Total nodesProxyPrefillDecode
2 · SLURM and Spurco-located11
3111
5113
7124
11146

Formula: prefill = max(1, (nnodes − 1) × 2 // 5), decode = nnodes − 1 − prefill. Two nodes are special-cased, because the formula would leave no decode node.

The tuning loop

  1. Start automatic. Run the default split and record prefill latency and decode throughput.
  2. Find the bottleneck. Prefill latency high: add prefill nodes. Decode throughput low: add decode nodes.
  3. Pin the split and rerun. Compare results against the baseline row.
json · custom 4P + 2D on 7 nodes
{
  "distributed": {
    "launcher": "sglang-disagg",
    "nnodes": 7,
    "nproc_per_node": 8,
    "sglang_disagg": { "prefill_nodes": 4, "decode_nodes": 2 }
  }
}
Validation rules. On Kubernetes, prefill + decode + 1 must equal nnodes (dedicated proxy). On SLURM and Spur, the sum may equal nnodes (co-located proxy) or nnodes − 1 (dedicated). Each side needs at least one node.

For MAD's own disaggregated cards, set xP and yD in env_vars and size the allocation with slurm.nodes to match.

Scheduler

  • SLURM: exclusive: true for benchmarks. enable_node_check: true runs a GPU health preflight that avoids OOM from stale processes. Setting nodelist skips the preflight.
  • Interactive: inside salloc, multi-node runs execute in place on the first nodes hosts.
  • Spur: put output_dir on shared storage and raise rendezvous_timeout if queue waits are long.

Kubernetes

  • host_ipc: true and a generous shm_size for NCCL. Request memory and cpu explicitly.
  • Multi-node needs a headless Service, which madengine creates. Results need a volume every pod can mount, ReadWriteMany for multi-node.
  • RDMA: a device plugin, IPC_LOCK rather than privileged, and host_network or a Multus network.
Pin what you compare. Same image digest, same driver stack, same node type. Then a change in perf.csv means something.
FAQ for the skeptical

Things that surprise people once

"I set -N 4 in args, but I got one node."

For slurm_multi, args is appended to the script, not forwarded to sbatch. Size the job with slurm.nodes or distributed.nnodes.

"My slurm block on run lost the card's node count."

On build, your block merges with the card's. On run, it replaces the card's block entirely. Restate nodes, GPUs and time.

"Kubernetes cannot pull my image."

The cluster needs a registry reference. A local ci-… tag exists only on the build host. Use --registry, or --use-image with a pushed image.

"The card says <supply-your-image>."

That is a placeholder, and madengine rejects it at submit time. Pass --use-image <ref> when you build.

"My env var did nothing on local Docker."

Local runs read docker_env_vars. A card's own env or env_vars block is not read on that path.

"Primus was rejected on SLURM."

It is a local single-node launcher by contract. Use torchtitan or megatron-lm for cluster pre-training.

"My failed run is missing from the report."

It should not be. Failures are written to perf.csv with status FAILURE. If a run died before that, check madengine cleanup --dry-run for leftovers.

"Two profilers gave odd results."

Do not combine rocprof* with rocm_trace_lite. Run a baseline, then one profiler at a time.

Rules of thumb

  • Build once, run many times from the manifest.
  • Add one block to change the target, not a new script.
  • Dry-run llm-d managed configs first.
  • Pick one GPU profiler, and keep a baseline.
  • nproc_per_node equals GPUs per node equals k8s.gpu_count.
  • Disaggregated: min 2 nodes on SLURM, 3 on Kubernetes.
  • Size slurm_multi jobs with nodes, never args.
  • Pin digests when comparing.
