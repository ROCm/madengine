The problem

The same model, five different ways to run it

A benchmark that works on a workstation rarely survives a move to a cluster. Image names, launchers, schedulers and result formats all change, and the number you report stops meaning the same thing.

01docker run by hand: device flags, mounts, environment
02sbatch scripts per cluster: modules, srun fan-out, rank variables
03Kubernetes manifests Jobs, PVCs, secrets, GPU resource names
04Serving stacks helm releases and gateways, as with llm-d
05Result formats every harness prints something different

With madengine: one model card, one flag changes

bash
# local Docker
madengine run --tags pyt_vllm_llama-3.1-8b_fp8

# SLURM: add a slurm block
madengine run --tags pyt_vllm_llama-3.1-8b_fp8 \
  --additional-context '{"slurm": {"partition": "gpu"}}'

# Kubernetes: add a k8s block
madengine run --tags pyt_vllm_llama-3.1-8b_fp8 \
  --additional-context '{"k8s": {"gpu_count": 1}}'

# llm-d: add an llm_d block
madengine run --tags pyt_vllm_qwen3-32b \
  --additional-context-file \
    examples/llm-d-configs/01-attach-existing-stack.json
Same model card. Same perf.csv. The context decides where it runs, and no code changes between targets.

Quick start

Four commands to a first number

Install madengine, clone MAD, find a model, run it. The container, the log scan and the result row come with it.

bash · from your MAD checkout
pip install git+https://github.com/ROCm/madengine.git
git clone https://github.com/ROCm/MAD.git && cd MAD

madengine discover --tags pyt_vllm_llama-3.1-8b_fp8

export MAD_SECRETS_HFTOKEN="<your Hugging Face token>"
madengine run --tags pyt_vllm_llama-3.1-8b_fp8 \
  --keep-model-dir --live-output

What happens

  1. Discover finds the card by name or tag in the catalog.
  2. Build makes the image from the card's Dockerfile.
  3. Run starts a container with a watchdog as PID 1.
  4. Results land in perf.csv. Failed runs are recorded as FAILURE, so every attempt appears.
Seven commands in all: discover build run report database cleanup setup-page. --live-output streams logs, --keep-alive leaves the container up for debugging.
Prerequisites: Docker, Python 3.9+, and ROCm or CUDA drivers. If ROCm is not auto-detected, set MAD_ROCM_PATH.
The pipeline

Build once, run anywhere

Build and run can be separate steps. The manifest carries the image and the Context that built it, so the same artifact runs on a workstation, a SLURM login node, or a cluster that only pulls from a registry.

discoverfind models by tag
buildimage per model
manifestbuild_manifest.json
runinfer target, execute
perf.csvone row per result
reportHTML · email · MongoDB
bash · split workflow
# CI or laptop: build and push
madengine build --tags pyt_vllm_llama-3.3-70b \
  --registry docker.io/myorg

# any target: run from the manifest
madengine run --manifest-file build_manifest.json
  • Pre-built images: --use-image <ref> or MAD_CONTAINER_IMAGE skips the build entirely.
  • Build on compute: --build-on-compute --registry … builds inside a SLURM job and pushes.
  • Pinned digests: --require-pinned-image pulls repo@sha256:… and fails instead of running a moved tag.
A cancelled run does not hold your GPU. A PID 1 watchdog stops the container when its heartbeat goes stale, signal handlers tear down containers and submitted jobs, and madengine cleanup sweeps anything left over.

Convention over configuration. There is no deploy flag. The first match wins, so moving a job between clusters is a diff of one block. Conflicting blocks are rejected before submission.

Clusters

Parallelism

Training and inference, templated or self-managed, with per-launcher environment contracts.

Analysis

Profilers

rocprof and rocprofv3 presets, rocm-trace-lite, Kineto traces with TraceLens, power and VRAM.

Supply chain

Pinned images

Digests recorded on every push. --require-pinned-image refuses a tag that moved.

Safety

Reliable runs

A log error scan stops a quiet crash reporting SUCCESS. A watchdog frees the GPU when a run is cancelled.

Output

Reports and history

One perf.csv schema, HTML and email reports, and a MongoDB upload.

Also built in: Hydra YAML config groups, data providers (local, NAS, MinIO, S3), and rocEnvTool environment capture.

Launchers

Three launcher contracts, ten names

A launcher is how a workload starts inside its own container, not the scheduler or the platform. Validation rejects a launcher on a target with no arm for it.

Contract 1

Templated

torchrun deepspeed megatron-lm torchtitan vllm sglang sglang-disagg vllm-disagg. The deployment templates render the start command.

Contract 2

Self-managed

slurm_multi. The card's own .slurm script starts its containers. Used by MAD's disaggregated and communication benchmarks.

Contract 3

Primus

primus. A local single-node run. The model script starts Primus. A cluster block is rejected.

Which launcher parallelizes what

Auto means madengine configures it. Manual means the launcher supports it, but your model script or config sets the degrees.

The additional_context cookbook

I want to… so I add…

I want toAdd to the Context
Build on a different base image"docker_build_arg": {"BASE_DOCKER": "…"}
Skip the build, run an image I have"MAD_CONTAINER_IMAGE": "repo:tag" or --use-image
Set env vars, local Docker"docker_env_vars": {"HSA_ENABLE_SDMA": "0"}
Set env vars on a cluster"env_vars": {"NCCL_DEBUG": "INFO"}
Mount weights or datasets"docker_mounts": {"/inside": "/on/host"}
Use a subset of GPUs or CPUs"docker_gpus": "0,2-4,7", "docker_cpus": "0-15"
Profile or trace the run"tools": [{"name": "rocprofv3_lightweight"}]
Run a script before or after"pre_scripts", "post_scripts"
Choose how it is parallelized"distributed": {"launcher": …, "nnodes": …}

Prefer a JSON file for anything with booleans or nesting. --config cannot be combined with --additional-context.
