madengine — Codebase Wiki

AI/ML model automation & benchmarking platform for local Docker, bare-metal conda, SLURM (and Spur), Kubernetes, and llm-d. A Typer-based CLI that discovers model cards, builds Docker images (or conda environments), runs them on a compute target, and writes structured performance results.

Entry point: src/madengine/cli/app.py::cli_main → console script madengine registered in pyproject.toml.

Reflects v2.4.0 + unreleased (develop) Python ≥ 3.8 7 commands Docker · bare-metal · SLURM/Spur · K8s · llm-d Typer + Rich + Hydra ROCm & CUDA Jinja2 templates

Version is derived from git tags at build time (versioningit); run madengine --version for the installed one. Where this page and the code disagree, the code wins — each section names the file it was derived from.

Overview

What madengine does

  1. Discover — finds model cards from models.json or dynamic get_models_json.py scripts and resolves tags (discover).
  2. Build — builds a Docker image per card (or adopts a pre-built one, or prepares a conda prefix for bare-metal) and writes build_manifest.json (build).
  3. Run — reads the manifest, infers the target from the context, runs the workload, and writes perf.csv (run, targets).
  4. Report & operate — HTML/email/TraceLens reports, MongoDB upload, orphaned-container cleanup, and a static model-picker page (report, cleanup / setup-page).

Build and run share one configuration spine — the additional_context dict — supplied as --additional-context, --additional-context-file, or a Hydra-composed --config (see additional_context and --config).

Quick start

Run these from a MAD-style project directory (one that contains models.json and/or scripts/). Every flag and key below is documented in the CLI and configuration sections.

# 1. Install (from the madengine repo checkout)
pip install -e .

# 2. List the cards a tag selects
madengine discover --tags dummy

# 3. Build and run in one command
madengine run --tags dummy \
  --additional-context '{"gpu_vendor":"AMD","guest_os":"UBUNTU"}'

# 4. Or build first (optionally push), then run from the manifest
madengine build --tags dummy --registry registry.example.com/ml
madengine run --manifest-file build_manifest.json \
  --additional-context '{"docker_gpus":"0,1,2,3"}'

No slurm, k8s, kubernetes or llm_d key and no platform → local Docker via ContainerRunner. gpu_vendor / guest_os default to AMD / UBUNTU when omitted.

madengine run --tags my_model --live-output \
  --additional-context '{
    "platform": "bare_metal",
    "conda": {"conda_bin": "/path/to/micromamba"}
  }'

Runs inside a conda/mamba/micromamba prefix on this machine; cannot be combined with slurm, k8s, kubernetes or llm_d. See Platforms.

madengine build --tags llama3 --registry registry.example.com/ml

# Multi-node torchrun via sbatch
madengine run --manifest-file build_manifest.json \
  --additional-context '{
    "slurm": {"partition":"gpu","nodes":4,"gpus_per_node":8,"time":"24:00:00"},
    "distributed": {"launcher":"torchrun","nnodes":4,"nproc_per_node":8}
  }'

# A card that drives its own per-node containers (slurm_multi):
# skip the local build; "auto" reads DOCKER_IMAGE_NAME from the card's env_vars
madengine build --tags pyt_sglang_disagg --use-image auto

A slurm key selects SlurmDeployment; add "scheduler": "spur" inside it for Spur. Launcher names are validated up front (unknown names exit 4). See SLURM, slurm_multi, launchers.

madengine run --tags llama3 \
  --additional-context '{"k8s":{"namespace":"ml-team","gpu_count":4}}'

A k8s (or kubernetes) key selects KubernetesDeployment; preset defaults are merged under your keys. The kubernetes Python client is installed with madengine. See Kubernetes for the sub-key table, storage layouts and secrets.

# Attach mode: benchmark an llm-d stack that already exists
madengine run --tags dummy_llm_d --additional-context '{
  "k8s":   {"namespace":"llm-d-bench","gpu_count":0},
  "llm_d": {
    "endpoint_url":"http://llm-d-inference-gateway.llm-d-bench.svc.cluster.local:80",
    "model":{"name":"Qwen/Qwen3-32B"}
  }
}'

An llm_d key wins over k8s. Without endpoint_url, madengine runs in managed mode and installs and removes helm releases itself. See llm-d.

# Context file (JSON object)
madengine run --tags llama3 --additional-context-file my_run.json

# Hydra / YAML frontend (same keys as the context, plus config groups)
madengine run --config my_job.yaml
madengine run --config my_job.yaml --config distributed.nnodes=4
madengine run --config my_job.yaml --config +env=nccl_debug

--additional-context is parsed as JSON first, then as a Python dict literal. --additional-context-file is merged under it (the inline string wins). --config cannot be combined with either. See CLI overview and --config.

git clone https://github.com/ROCm/madengine.git

python3 -m venv venv && source venv/bin/activate

# Editable install: ALL runtime and dev dependencies come with it
pip install -e .

# Optional: host-side TraceLens analysis (see "madengine report tracelens")
pip install -e '.[tracelens]'

Run madengine from the root of a MAD-style model repository (the directory holding models.json and scripts/), or point MODEL_DIR at it (see Environment variables).

Requirements

  • Python ≥ 3.8 (requires-python; Black targets py38–py311, mypy checks as 3.8).
  • Docker with GPU access (ROCm: /dev/kfd + /dev/dri; NVIDIA: container toolkit) for the default container platform.
  • conda / mamba / micromamba instead of Docker for "platform": "bare_metal" (see Platforms).
  • Per target: SLURM (or Spur) CLI on the submit host; kubectl and a kubeconfig for Kubernetes; helm for managed llm-d stacks.

Dependencies and extras

Everything is declared in pyproject.toml under [project] dependencies, including the Kubernetes client, Hydra, MongoDB, and the dev toolchain. There is exactly one optional extra:

Versioning

The version is not stored in the source tree. versioningit derives it from git tags matching v<version> (default tag v2.0.0 when none exists). Untagged commits become <base>.post<distance>+g<sha>; a dirty tree adds a build date (<base>+d<YYYYMMDD> on a tag, …+g<sha>.d<YYYYMMDD> after it). madengine --version and madengine.__version__ read the installed package metadata, so an uninstalled checkout reports unknown / dev.

Architecture diagram

Key data flows

Derived from orchestration/build_orchestrator.py and orchestration/run_orchestrator.py. Both orchestrators receive a single merged additional_context dict from the CLI (see additional_context).

Build flow (BuildOrchestrator.execute)

  1. Constructor: merge context sources, fill build defaults (gpu_vendor=AMD, guest_os=UBUNTU when absent), run ConfigLoader.load_config() (infers target, rejects conflicting blocks such as k8s + slurm or llm_d + slurm, applies presets). The keys the user really set under slurm are remembered separately from preset defaults.
  2. Context(build_only_mode=True): no GPU or NUMA detection. MAD_SYSTEM_GPU_ARCHITECTURE is auto-detected only when the build is part of madengine run --tags (detect_local_gpu_arch=True) and the user did not supply it.
  3. Dispatch on mode, in this order:
    • platform: bare_metal → create conda prefixes, no Docker (see Execution platforms).
    • --use-image (or auto) → write a manifest for an existing image, no build.
    • --build-on-compute → build and push from a SLURM compute node (needs --registry).
    • Otherwise the normal Docker build below.
    --use-image together with --build-on-compute raises ConfigurationError.
  4. Normal build: DiscoverModels.run() runs once and is reused. Cards whose distributed.launcher is a self-managed launcher (slurm_multi) need an image source: with no --registry, a single env_vars.DOCKER_IMAGE_NAME on the cards becomes an implicit --use-image (angle-bracket placeholders are rejected); otherwise ConfigurationError.
  5. Warn when a selected Dockerfile declares ARG MAD_SYSTEM_GPU_ARCHITECTURE with no default and no value was resolved.
  6. DockerBuilder.build_all_models() builds every matching Dockerfile per card, optionally pushes, and never aborts on a single failure (see Docker build).
  7. Manifest steps, always executed even after partial failure: export_build_manifest() → save summary → save deployment_config → merge the first built card's distributed / slurm fields into deployment_config (user-set values win).
  8. Raise BuildError only when all builds failed. A partial build exits successfully with a warning.

Run flow (RunOrchestrator.execute)

  1. Start a SessionTracker: records how many rows perf.csv already has (marker file .madengine_session_start beside it) so the CLI can show only this run's rows.
  2. Manifest source, in priority order: MAD_CONTAINER_IMAGE in context (needs --tags; validates or pulls the image, writes a synthetic manifest with local_image_mode); else an existing --manifest-file; else build first (--tags). Neither tags nor a manifest → ConfigurationError.
  3. _load_and_merge_manifest(): runtime context overrides the stored deployment_config for deploy slurm k8s kubernetes llm_d platform conda distributed vllm env_vars debug; tools, pre_scripts, post_scripts, encapsulate_script, require_pinned_image are written into manifest context. A runtime slurm block replaces the stored one wholesale and resets the explicit-key provenance.
  4. Stored deployment_config keys the runtime did not set are copied into the working context.
  5. Target inference (see Deployment targets): platform: bare_metal → llm_d → k8s/kubernetes → slurm (spur when slurm.scheduler or deploy is spur) → a self-managed launcher on the first built card implies slurm → otherwise local. A legacy deployment_config.target is the final fallback.
  6. Dispatch:
    TargetExecutor
    local / dockerContainerRunner.run_models_from_manifest()
    bare_metalBareMetalRunner.run_models_from_manifest()
    slurm, spur, k8s, llm-dDeploymentFactory.create(DeploymentConfig).execute()
  7. Always, in a finally-style path: _cleanup_model_dir_copies() removes the madengine-provided files under scripts/common/.

Local Docker path (_execute_local)

  1. Runtime Context (full system + GPU detection), optional data.json loaded as Data, node info table.
  2. Restore host-level fields from the manifest context without overriding runtime-detected values: docker_mounts, docker_build_arg, docker_gpus, gpu_vendor, guest_os, docker_env_vars; tools / scripts always come from the manifest unless the runtime context supplies its own.
  3. Filter built_images: GPU vendor/architecture compatibility (orchestration/image_filtering.py; an image without gpu_vendor is treated as compatible), then skip_gpu_arch from each card (unless --disable-skip-gpu-arch). Skipped cards are written to perf.csv with status SKIPPED. The whole step is best effort: any exception, including the ExecutionError raised when no image is compatible, is caught, printed as a warning, and the run proceeds with all images.
  4. _copy_scripts(): honours an external MODEL_DIR (merges its docker/ and scripts/ into the cwd) and copies pre_scripts, post_scripts, tools, entrypoints, tools.json, test_echo.sh from the madengine package into scripts/common/. The MAD project's own scripts/ and docker/ are never deleted.
  5. --wait-for-gpu-memory gate (local only), then ContainerRunner runs each manifest entry. Distributed targets print a warning and ignore --keep-alive, --keep-model-dir, --skip-model-run and --wait-for-gpu-memory.
  6. For a full workflow the build and run logs are merged into one *.live.log.

Distributed path (_execute_distributed)

  1. For target slurm only, skip_gpu_arch is decided before submission (a filtered per-run copy of the manifest is submitted; the build manifest is left intact). Skipped cards appear as SKIPPED rows. An empty manifest returns a FAILURE row instead of exiting 0. Spur, Kubernetes and llm-d do not apply this pre-filter.
  2. Manifest context.docker_env_vars are handed to the deployment layer (runtime keys win), because SLURM/K8s never enter the local restore step.
  3. Session baseline is measured on the working perf.csv (what the deployment appends to), and this run's rows are exported to --output afterwards when it names another file.
  4. DeploymentConfig carries timeout (resolved against the default) and cli_timeout (verbatim, so the inner madengine run on the node still lets the model card outrank the default); monitor and cleanup_on_failure (both default true) are read from context.
  5. If the scheduler fails before reporting per-model metrics, every manifest model not already reported is added to failed_runs, so the CLI exit code is not 0 for a failed job.

Per-backend job flow (sbatch template, array jobs on Spur, Indexed Jobs on K8s, helm for llm-d): see SLURM, Kubernetes, llm-d.

Global behavior

  • madengine --version prints the installed package version (importlib.metadata; unknown if not installed). With no sub-command the help is shown. Shell completion is disabled (add_completion=False).
  • cli_main() first calls core.lifecycle.install_signal_handlers() so SIGINT/SIGTERM/SIGHUP tear down benchmark containers (see container lifecycle). A KeyboardInterrupt or an unhandled exception that escapes a command exits 1.
  • A Rich traceback handler is installed with show_locals=True. An unhandled crash can therefore print local variable values; do not rely on the console log being free of credentials.

Context sources

build and run accept the same configuration spine through three mutually exclusive-in-part inputs:

InputFormatRules
--additional-context, -cString; parsed as JSON first, then as a Python dict literal (ast.literal_eval)Must be an object at top level. Empty / {} counts as "not given".
--additional-context-file, -fJSON file (object)Loaded first; the -c string is deep-merged over it (CLI wins key by key, nested dicts merge rather than replace).
--config (repeatable)YAML file and/or Hydra overridesCannot be combined with either input above (exit 4). See --config frontend.

Validation applied to the merged context

Implemented in cli/validators.py::finalize_additional_context_dict; any failure exits 4 (INVALID_ARGS). build always validates; run validates only when a non-empty context was supplied.

  1. Missing gpu_vendor / guest_os are defaulted to AMD / UBUNTU (core/additional_context_defaults.py) and a banner says so.
  2. Structure checks: docker_build_arg, docker_env_vars, docker_mounts, env_vars, k8s, slurm, kubernetes, llm_d, distributed, vllm, deployment_config, deploy must be objects; tools and pre_scripts arrays; docker_gpus and MAD_CONTAINER_IMAGE strings; timeout a number; debug a boolean; log_error_patterns a non-empty string array. Build-arg values are coerced to strings.
  3. gpu_vendor must be AMD or NVIDIA, guest_os must be UBUNTU or CENTOS (case-insensitive, normalized to upper case).
  4. Launcher: every distributed.launcher / launcher.type is validated and rewritten to its canonical spelling. An unknown name is rejected up front rather than running as a single process. A bare-string top-level launcher is rejected. The per-target rule (slurm_multi is not valid on llm-d) is enforced when the deployment is constructed. See Launchers.
  5. Platform: platform is a string; omitted means Docker, "bare_metal" selects conda. Unknown values, the retired top-level bare_metal object, and a conda block on a Docker run are rejected. See Platforms.

Discovery sources

  1. Root ./models.json — required.
  2. scripts/**/models.json — found by a recursive walk, so nested submodule layouts (scripts/MAD/…) work.
  3. scripts/**/get_models_json.py — dynamic; must define list_models() returning CustomModel objects (utils/discover_models.py).

A directory containing both models.json and get_models_json.py is an error. If MODEL_DIR points elsewhere than the current directory, discovery first copies docker/, scripts/, models.json, credential.json and data.json from it into the working directory.

Self-managed launchers need an image source

For a card whose launcher is slurm_multi, the build requires one of: --registry, --use-image, --build-on-compute --registry, or a single env_vars.DOCKER_IMAGE_NAME on the card(s). In the last case, with no registry given, it is used as an implicit --use-image. Otherwise the build raises ConfigurationError (exit 4). An angle-bracket placeholder such as <your-image> in DOCKER_IMAGE_NAME is rejected.

Exit status

0 only if every build succeeded and every push succeeded. Any failure, including a partial one, exits 2; images that did build remain in the manifest.

CLI — run

Runs models and writes perf.csv. Mode is chosen by the manifest:

  • --manifest-file names an existing file → execution only (--tags is not used to select models).
  • Otherwise → full workflow: build, then run. A named-but-missing manifest only prints a warning. With neither a manifest nor --tags (and no MAD_CONTAINER_IMAGE) the orchestrator raises ConfigurationError (exit 4).
  • MAD_CONTAINER_IMAGE in context skips the build and synthesizes a manifest for the given image; --tags is then required.

Timeout resolution

Single definition in core/timeout.py::resolve_run_timeout, shared by local, SLURM and Kubernetes runs. Precedence, lowest to highest: default (DEFAULT_RUN_TIMEOUT = 7200 s) < model card timeout < explicit --timeout.

--timeoutEffect
-1 (default)"Not passed": falls through to the card's timeout, else 7200 s.
0No timeout, overriding the card.
Positive integerThat many seconds, overriding the card (even 7200, which is distinguishable from omitting the flag).
Below -1Rejected, exit 4.

A card may itself set "timeout" to 0 or any non-positive value to mean "unbounded"; null in an old manifest is ignored. Non-positive resolved values are mapped to "no timeout" for subprocess by subprocess_timeout() (since subprocess would treat 0 as "expire immediately").

Exit status

0 when every model succeeded; 3 if any model failed; 2 when every build of a full workflow failed (BuildError); 4 for invalid arguments/configuration; 1 otherwise. A full workflow whose build only partly failed still runs the images that built; if those runs all pass it exits 1 ("Workflow failed for unknown reasons"), not 2. After the run, run prints the per-model results table and the perf.csv table (current-session rows highlighted via utils/session_tracker.py).

Validation and restrictions

  • Unknown top-level keys are errors (Unknown config key: '…'). Allowed: defaults, platform, scheduler, hardware, launcher, model, docker, build, env_vars, debug, live_output, log_error, tools, pre_scripts, post_scripts, encapsulate_script, data_config, output, summary_output, gpu_vendor, guest_os, runtime, slurm, k8s, kubernetes, distributed, vllm, sglang_disagg, shared_data, timeout, gpu_type, gpu_memory_gb, gpus_per_node, data, require_pinned_image.
  • slurm together with k8s/kubernetes is rejected.
  • distributed.enabled: true requires distributed.launcher; distributed.nnodes must be a positive integer.
  • Platform: the object form platform: {type: …} accepts only docker; bare_metal, podman and singularity are rejected as "not yet supported", so the platform=bare_metal group fails validation. A top-level platform value is CLI metadata and is not forwarded into additional_context, and conda is not an accepted key, so bare metal cannot be selected through --config: pass "platform": "bare_metal" (and any conda block) with --additional-context.
  • Any validation problem is raised as ConfigurationError listing every error (exit 4).

Launcher handling

  • The launcher top-level key as a string is the Hydra group selector and is dropped from the context. As an object (type, master_port, …) it is kept as launcher for Kubernetes.
  • distributed.launcher is canonicalized by the same function the engine uses elsewhere (sglang_disagg → sglang-disagg, slurm-multi → slurm_multi). The group launcher=megatron yields megatron-lm; the bare string megatron is not a valid launcher name.
  • distributed.enabled is passed through as written; the translator never sets it. Every launcher group writes enabled: true, and the default launcher=none writes enabled: false. Validation requires a launcher when it is true. Kubernetes profile selection treats either enabled: true or a launcher name as distributed.
  • launcher=native (and docker) is a perf.csv reporting value, not a launcher. The translator forces distributed.enabled: false and launcher: null so a Kubernetes profile cannot inject torchrun. Do not copy that group into JSON.
Gotchas: --config needs hydra-core / omegaconf (declared dependencies). runtime from a hardware group is kept as metadata only and is not forwarded to additional_context. The groups disagree on the port key: torchrun writes both port and master_port, sglang / sglang_disagg write only port, the rest only master_port. SLURM reads port first and falls back to master_port; Kubernetes prefers master_port (including launcher.master_port) and falls back to port. A disagreeing pair is not rejected. The sglang_disagg group puts its split under a top-level sglang_disagg key, which the SLURM and Kubernetes launchers do not read; set distributed.sglang_disagg.prefill_nodes / decode_nodes to change the split. Likewise the vllm group's top-level vllm block is only stored in deployment_config.

additional_context — configuration spine

How it is parsed

InputParsing
--additional-context '<string>'CLI validator (cli/validators.py) tries json.loads first, then ast.literal_eval. Both {"a": true} and {'a': True} are accepted. The top level must be an object; anything else exits with code 4.
--additional-context-file FILEStrict JSON object (json.load).
Both givenFile first, then the string deep-merged on top key by key (CLI wins). A file with slurm.partition plus a string with slurm.nodes yields both.
--configHydra frontend builds the same dict; mutually exclusive with the two flags above. See config frontend.
Inside the orchestratorsThe merged dict is passed to Context as repr(dict), which parses it with ast.literal_eval. Values must therefore be literals (strings, numbers, booleans, lists, dicts, None).
Quoting tip: prefer JSON in single quotes ('{"docker_gpus": "0,1"}') or a file. Python-literal strings such as "{'k': True}" also work, but unquoted shell expansion of True/False inside bare words does not.

What Context adds

core/context.py merges user values over detected ones; user-provided values are never overridden by detection.

Build-only mode (madengine build)

  • No GPU/NUMA detection (so CPU-only build nodes work). Detects ctx_test and host_os when absent, best effort.
  • gpu_vendor / guest_os default to AMD / UBUNTU (core/additional_context_defaults.py) so Dockerfile context filtering has values.
  • Reads every MAD_SECRETS* environment variable into docker_build_arg and docker_env_vars.

Runtime mode (madengine run)

  • Detects ctx_test, host_os, numa_balancing, gpu_vendor (NVIDIA via nvidia-smi, AMD via amd-smi then rocm-smi), rocm_path (see ROCm path).
  • Fills docker_env_vars: MAD_GPU_VENDOR, MAD_SYSTEM_NGPUS, MAD_SYSTEM_GPU_ARCHITECTURE, MAD_SYSTEM_HIP_VERSION, MAD_SYSTEM_GPU_PRODUCT_NAME (only if not already set); mirrors the architecture into docker_build_arg.
  • Defaults docker_gpus to "0-<N-1>" and computes gpu_renderDs (GPU index → /dev/dri/renderD*).
  • Detection failure raises RuntimeError on the runtime node.
Secrets: MAD_SECRETS* values are dropped (not masked) from the manifest context by manifest_safe_context(); at run time Context reads them from the environment again.

Result status and log scanning

  1. Performance is extracted from the log with the pattern performance: <number> <metric> (fallback: HuggingFace train_samples_per_second), or from the multiple_results CSV.
  2. Container lifecycle & cancellation

Implemented in core/lifecycle.py and core/docker.py. Problem solved: a cancelled CI job kills madengine's process tree, but the detached benchmark container survives, keeps /dev/kfd open and blocks the next job on the GPU. Three layers, most to least robust:

LayerMechanismSurvives SIGKILL of madengine?
1. Dead man's switchContainer PID 1 is a POSIX sh loop watching /myworkspace/.madengine_heartbeat.<container>. A host thread rewrites it every MADENGINE_HEARTBEAT_INTERVAL s. The container exits when the file is missing or older than MADENGINE_HEARTBEAT_STALE_AFTER s. One file per container, so closing one never stops another started from the same directory.Yes
2. Signal handlersInstalled by cli_main() for SIGINT/SIGTERM/SIGHUP: drop heartbeats, reap registered containers within a 6 s budget, run registered cancel hooks, os._exit(130). A second signal exits immediately.No
3. reap() / madengine cleanupBounded escalation shared by the handlers, normal teardown and the cleanup command.Manual / cron

Teardown escalation

  1. An already-exited container just gets docker rm -f. A live one gets docker stop -t 1 (10 s budget) → docker kill -s KILL (10 s) → docker rm -f (15 s); each step runs only if the container is still present.
  2. If the daemon cannot remove it: read the container's host PIDs from the cgroup (works with a hung dockerd), SIGKILL them, retry docker rm -f.
  3. Every docker call has a hard deadline and its own session, because a wedged GPU blocks the daemon too. An overall deadline caps the whole escalation.
  4. docker inspect failure means unknown state, not "gone".

GPU wedged

Processes in uninterruptible sleep (D state) inside the GPU driver cannot be killed from userspace. A wedge is reported only on evidence: D-state host PIDs, or a container still in a live state after stop, kill and rm. An unresponsive daemon alone is not enough.

  • Marker gpu_wedged.json (container, stuck PIDs, session, hostname, timestamp) is written to the state dir.
  • madengine cleanup exits 5 (ExitCode.GPU_WEDGED) so CI can pull the runner out of rotation; the host needs a reboot.

Docker build

Implemented in execution/docker_builder.py (DockerBuilder); orchestrated by BuildOrchestrator (see flows).

Image selection & naming

  • Candidates are ls <card.dockerfile>.*, kept only if they are this card's own variants: <prefix>.Dockerfile, <prefix>.<os>.<vendor>.Dockerfile, or with a same-card noctx/ctx<token> segment. A sibling card whose Dockerfile name merely starts with this prefix is not built.
  • Survivors are filtered by the Dockerfile's # CONTEXT {...} header against the context (gpu_vendor, guest_os, ...).
  • Local tag: ci-<name, lowercased, / → _>_<Dockerfile basename without .Dockerfile>. With --target-archs a _<arch> suffix is appended.
  • Log file: <name>_<dockerfile>.build.live.log in the cwd.

Registry names

  • --registry docker.io|dockerhub: <repository>:<local tag>, repository from credential.json / MAD_DOCKERHUB_REPO (placeholder repositories are ignored).
  • Any other registry: <registry>/<repository>:<tag> when credential.json has a repository for it, else <registry>/<local tag>.
  • A batch-build entry's registry_image / registry overrides both.

The docker build command

docker build [--no-cache] --network=host \
  [--build-context tools=docker/common] \
  -t <tag> --pull -f <dockerfile> \
  <--build-arg ...> <context>
  • --build-context tools=docker/common is emitted only when docker/common/ exists relative to the cwd, so Dockerfiles can COPY --from=tools .... Projects without that directory get no flag and do not fail.
  • Build args, lowest to highest precedence: card docker_build_arg, then --target-archs arch and cred args, then context docker_build_arg (which also carries MAD_SECRETS* from the environment and the detected MAD_SYSTEM_GPU_ARCHITECTURE). All values are shell-quoted.
  • Context: dockercontext, else ./docker; . for Dockerfiles with primus in the name.
  • build_command in the manifest has MAD_SECRETS* and token-shaped values masked.
  • If the base image's registry is not authenticated, a login is attempted first; an existing ambient docker login is left alone. A registry-denial in the log produces an actionable hint.

  • docker tag + docker push (no timeout). A push failure marks the entry push_failed and does not fail the build; it is listed in push_failures and summary.failed_pushes.

  • image_size_bytes is recorded so the SLURM node health check can compare it with free disk on each candidate node.

Build-time validation

BuildOrchestrator runs ConfigLoader.load_config(), which calls infer_and_validate_deploy_type() and applies the SLURM or K8s presets. It raises (surfaced as ConfigurationError) when:

  • k8s/kubernetes and slurm are both present;
  • llm_d and slurm are both present;
  • an explicit deploy value contradicts the blocks: k8s/kubernetes without a k8s block, slurm/spur without a slurm block, spur with a slurm.scheduler other than spur, or local with a scheduler block;
  • slurm.scheduler is anything other than slurm or spur.

Gotchas
  • --force-mirror-local is not a target override. It is a data-provider flag (force_mirrorlocal) that forces local mirroring of a dataset; the SLURM template also forwards it as --force-mirror-local <shared_data>. There is no CLI flag that forces local execution when a scheduler block is present: remove the block.
  • The kubernetes spelling selects the K8s target, but its sub-keys are not read: presets always create a k8s block, which wins. Put sub-keys under k8s.
  • --keep-alive, --keep-model-dir, --skip-model-run and --wait-for-gpu-memory have no effect on distributed targets; a warning lists the ignored flags.
  • For SLURM, skip_gpu_arch is applied before submission, for every launcher including slurm_multi; skipped cards appear as SKIPPED rows.

SLURM & Spur deployment

Implemented by SlurmDeployment in deployment/slurm.py (node preflight in slurm_node_selector.py) and its subclass SpurDeployment in spur.py. madengine drives the scheduler through its local CLI (sbatch, squeue, sacct, scontrol, srun, scancel): run it on a login node; no SSH and no Python SLURM library are involved. The target is chosen by the presence of a slurm key (see Deployment target inference). The sbatch script is rendered from deployment/templates/slurm/job.sh.j2.

madengine must be on PATH of the compute nodes. Activate the virtual environment before madengine run.

  3. Single node.   4. Multi node. Writes <output_dir>/madengine_task_<job tag>.sh and runs srun bash <task script>. Each task sets NODE_RANK=$SLURM_PROCID, emits the launcher's environment (MAD_MULTI_NODE_RUNNER etc.), rsyncs the project (excluding .git, caches, virtualenvs, old logs) into a node-local workspace madengine_job_<tag>_node_<rank>, builds the same local manifest, sets MIOPEN_USER_DB_PATH=/tmp/.miopen/node_<rank>_rank_<local> and TORCH_ELASTIC_RDZV_TIMEOUT=3600, and calls madengine run with output redirected to madengine-<model>_<tag>_node_<rank>.{out,err}. Node health preflight

deploy() runs SlurmNodeSelector before sbatch when enable_node_check is true, slurm.nodelist is unset, the scheduler is not Spur, and the run is not in place. It lists idle candidate nodes in the partition (honouring exclude and constraint, at most 100 candidates) and probes them one by one with srun --nodelist=<node> --overlap until enough are clean.

HealthMeaning
CLEANUsable.
DIRTYA GPU with more than 50 GB VRAM in use (read from amdgpu sysfs), or, without sysfs, stale ray::/RayWorkerWrapper/raylet/vllm processes; or Docker's data root has less free space than the largest image to pull and the image is not already present.
UNREACHABLE / UNKNOWNThe probe could not run or its output could not be read.
  • Unhealthy nodes are appended to the job's --exclude. With enough clean nodes the job is pinned to them via --nodelist.
  • Multi-node gate: fewer clean nodes than nodes fails the run ("Not enough clean nodes") unless allow_submit_without_clean_nodes is true. Single-node runs are never gated.
  • Inconclusive checks stand down: if every examined node was unreachable/unknown the check is disregarded (no gate, no pin); measured dirty nodes stay excluded.
  • auto_cleanup_nodes stops only containers labelled madengine.session and kills Ray, vLLM and SGLang processes on a dirty node.
  • Probe jobs are named madengine_nodecheck_<pid>_<time> and always cancelled afterwards.

Admins can additionally install scripts/slurm/epilog.sh as a SLURM epilog to clear stray GPU processes after every job (setup notes in scripts/slurm/SLURM_EPILOG_SETUP.md).

Submission, monitoring and results

  • Submit: sbatch <output_dir>/madengine_<model>.sh. Transient Raft-leader errors ("not the raft leader", "no leader elected", "service is currently unavailable") are retried up to 6 times, 5 s apart.
  • Monitor: BaseDeployment polls every 30 s. squeue -j states RUNNING, PENDING, CONFIGURING, COMPLETING mean keep waiting; COMPLETED is success; any other state (FAILED, CANCELLED, TIMEOUT, NODE_FAIL, ...) is failure. When the job has left the queue the final state comes from sacct -j <id> -n -X -o State, retried 3 times 5 s apart; -X is dropped if the scheduler rejects it. No row at all gives status UNKNOWN, never an assumed success.
  • Results are always collected, even for failed jobs, so failed runs are recorded in perf.csv. The login-node process parses the collected per-node logs and multiple_results CSVs under <output_dir>/<model>/<job id>/node_<rank>/, builds one run record and writes it through the same reporting pipeline as local runs (perf.csv, perf_super.csv/json), so a single cumulative file serves local and distributed runs.
  • Cancel (Ctrl-C, SIGTERM, CI cancel): the lifecycle handler runs cleanup(), which issues scancel <job id>. Inside an allocation the allocation itself is never cancelled; the in-place process group is signalled instead (see below).
  • skip_gpu_arch: for non-Spur SLURM runs the orchestrator drops cards whose skip_gpu_arch names the nodes' architecture before submission (a card on the wrong architecture is reported SKIPPED, not submitted). The filtered manifest is a unique per-run copy <manifest stem>.skip_gpu_arch.<pid>.<uuid>.json beside the build manifest; the build manifest is left untouched, and a failure to write the copy aborts instead of falling back to the original. --disable-skip-gpu-arch turns this off.

When SLURM_JOB_ID is set madengine detects the allocation and sizes it with scontrol show job (falling back to SLURM_JOB_NUM_NODES, SLURM_NNODES, then the node list). Requesting more nodes than the allocation holds fails; fewer is allowed and prints a note.

Kubernetes deployment

Implemented by KubernetesDeployment in deployment/kubernetes.py, composed from mixins. It renders Jinja2 manifests, applies them with the Kubernetes Python client, streams logs, and reads results back through pod logs, kubectl and a results volume. The kubernetes package ships as a core dependency; if it fails to import, the target is unregistered (see Target inference).

Lifecycle (BaseDeployment.execute())

  1. validate — cluster reachable, namespace exists, at least one node advertises gpu_resource_name. madengine never creates a namespace. The GPU-node check blocks CPU-only models too (llm-d attach mode skips it).
  2. prepare — renders ConfigMap, Job and (multi-node) headless Service.
  3. deploy — deletes this job's leftovers, creates the results PVC, Secrets, ConfigMap, Service, then the Job.
  4. monitor — polls the Job; with --live-output it streams pod logs. A Job is finished only on the Complete condition (or succeeded >= completions); Failed condition means failure. A non-zero succeeded count alone is not completion.
  5. collect results — always runs, even after failure, so failed runs are recorded.
  6. cleanup — on deploy failure or Ctrl-C/cancel only: deletes the Job, ConfigMap and Service. After a successful run the Job and its PVC stay unless ttl_seconds_after_finished is set; the next run of the same model replaces them.

Secrets and image pulls

  • With from_local_credentials and a credential.json in the working directory, deploy creates <job>-runtime (mounted at /workspace/credential.json) and, if it holds usable Docker Hub credentials, <job>-registry-pull. Both carry app=madengine. Without the file, no Secret is created and an empty {} credential payload goes into the ConfigMap.
  • There is no top-level secrets context key that turns arbitrary values into a Kubernetes Secret. Put credentials in credential.json, or pre-create a Secret and point k8s.secrets at it.
  • The pod must be able to pull the image. A local ci-… tag or a placeholder such as <your-image> is not pullable: build with --registry or pass a registry reference with --use-image, or the run fails with a ConfigurationError naming the push error. require_pinned_image in the context makes pods pull by digest.

Names and multi-node

  • Job name is madengine-<sanitized model>, capped at 63 characters (Batch Jobs require the job-name label to equal metadata.name); long names are shortened with a hash. The headless Service, pod subdomain and container name share one DNS-label form of it. The ConfigMap is <job>-config.
  • nnodes > 1 makes an Indexed Job (completions=parallelism=nnodes) with a headless Service and pod subdomain so <job>-0 resolves. sglang-disagg always gets the Service and needs at least 3 nodes (pod 0 is a dedicated proxy).
  • vLLM and SGLang are per-replica launchers: each node reports its own metric and results are aggregated across pods.
  • Launcher shape is resolved from launcher.type / launcher.nnodes (older form), then distributed in the run context, then the manifest's deployment_config.distributed, field by field. A runtime distributed block wins over the manifest, and n_gpus: -1 is not used as a process count.
  • The model script directory is bundled recursively (text files only) into the ConfigMap; a payload beyond about 1 MiB is rejected before submission.

Leftovers, cancel and results

  • Names are deterministic, so a rerun replaces its own Job, Secrets, ConfigMap, Service, collector pod and results PVC. Everything madengine creates is labelled app=madengine; a same-named object without that label stops the deploy instead of being deleted (older unlabelled Secrets and collector pods are accepted). Use another namespace in that case.
  • Results land under ./k8s_results/<job>/<pod>/: pod.log, a pvc/ mirror, and log_csv/ files rebuilt from MADENGINE_PERF_CSV_BEGIN/END blocks the pod printed when no volume copy survived.
  • The card's timeout (or --timeout) is applied inside the pod with timeout; 0 means unbounded.
  • If the Kubernetes API is unreachable during cleanup, delete by hand: kubectl delete job,configmap,service -l app=madengine -n <ns> (scope with --context if you use several clusters).

slurm_multi on Kubernetes

A slurm_multi card ships its own SLURM batch script that fans out with srun and starts one docker run per node. On Kubernetes madengine runs that script unchanged: one pod per node (an Indexed Job with a headless Service), the script on pod 0, and stand-ins for srun, docker and scontrol first on PATH. Code: deployment/k8s_slurm_multi.py and deployment/k8s_shim/. Select it by giving a card (or distributed.launcher) the slurm_multi launcher together with a k8s block.

How it runs

  1. prepare() builds a ConfigMap holding a tarball of the card's script directory, any include_script_dirs, and the shim; a headless Service (publishNotReadyAddresses, port 29711); and an Indexed Job.
  2. Every pod unpacks the bundle and runs mad_k8s_node.sh, which exports SLURM_JOB_ID, SLURM_JOB_NODELIST, SLURM_NNODES, SLURM_PROCID, SLURM_NODEID and related variables.
  3. Pods 1..N-1 serve tasks from a small TCP agent. Pod 0 starts its own agent, waits for all peers, then runs the card script from the script's directory with the card's args.
  4. The shim's srun sends a task to each named pod's agent and returns the highest exit status. docker run runs the command in that pod: the pod is the container.
  5. Pod 0 publishes /results/<job>-0/perf.csv and exit_code, then tells the peers to shut down.

slurm_multi launcher on SLURM

What it is

An escape hatch for workloads that orchestrate their own per-node Docker containers with srun (for example SGLang or vLLM disaggregated serving: proxy, prefill and decode). madengine does not use job.sh.j2 and does not start a container: it generates a small wrapper that runs the card's own .slurm/.sh script directly on the head node, on bare metal, so the script can call srun/scontrol itself without nesting.

It is not a peer of the templated launchers: madengine builds no launcher command for it.

On Kubernetes the same card runs as an Indexed Job; see slurm_multi on Kubernetes.

How to select it

{
  "slurm": {"partition": "gpu", "nodes": 3, "gpus_per_node": 8, "time": "02:00:00"},
  "distributed": {"launcher": "slurm_multi"}
}

Accepted spellings: slurm_multi and the alias slurm-multi (normalised). The launcher may come from the card's distributed block or the run context; the deployment config wins over the card. A card that names the launcher but has no slurm block is still treated as a SLURM deployment. It is rejected on llm-d.

The generated wrapper

  1. Header: --job-name=madengine-<model>, --nodes/--ntasks = resolved node count, --export=ALL, --gpus-per-node (unless skip_gpus_directive), --time, --exclusive (default), and reservation, nodelist, qos, account when set. slurm.nodes is sized from distributed.nnodes when not set explicitly; an explicit slurm.nodes wins with a warning; invalid nnodes is rejected.
  2. unset SLURM_EXCLUSIVE (otherwise every srun inside re-parses it as a step request and fails with "Invalid --exclusive specification"), then module load for slurm.modules.
  3. Environment exports, lowest to highest precedence: layered config (mad-config.yaml), manifest context.docker_env_vars, the card's env_vars, then additional_context.env_vars minus keys only a preset supplied (so the multi-node preset's NCCL_IB_DISABLE=1, NCCL_SOCKET_IFNAME=eth0, HSA_ENABLE_SDMA=0 do not override the card's own fabric detection). Also: xP/yD from distributed.sglang_disagg (prefill_nodes/decode_nodes) when the script has not set them, and MAD_TOOLS=<names> when tools are configured and rocprofv3 is available (madengine cannot wrap a script it does not control; the script decides). Values are shell-quoted.
  4. Node addressing (stock SLURM): MAD_NODE_IPS (rank-ordered, loopback addresses rejected), IPADDRS, SGLANG_NODE_IPS and MAD_NODE_RANK, each only if not already set. Spur builds the equivalent through its rendezvous directory.
  5. Image staging for registry images: one srun --ntasks=$SLURM_NNODES --ntasks-per-node=1 step that logs in using MAD_DOCKERHUB_USER/MAD_DOCKERHUB_PASSWORD (or MAD_DOCKER_USER/MAD_DOCKER_TOKEN; only the names are written to the script, values arrive through --export=ALL), skips nodes that already hold the image, and otherwise pulls. Spur pulls locally in each array task. DOCKER_IMAGE_NAME comes from the registry reference recorded by the push, else an already-resolved card value, else the card's docker_image. With require_pinned_image it is pinned to the build digest.
  6. Run: cd into the script's directory, delete a stale multiple_results file (unless it is one of madengine's own cumulative reports), then bash <script> <args> with set +e so the exit code is always captured. The script name and args are shell-quoted. A madengine_<model>_<job id>.complete marker (exit_code=, timestamp=) is written to slurm.output_dir, and the wrapper exits with the script's exit code.

Results aggregation

The card's script writes the full perf schema itself, so it is read directly rather than merged with common run info (re-deriving status from performance would turn a legitimate zero-score FAILURE into SUCCESS). The first source found wins:

  1. The card's multiple_results, searched in the script's directory, <output_dir>/<job id>, <output_dir> and the current directory. A file older than this submission (30 s clock-skew slack) is ignored as stale.
  2. perf*.csv in slurm.results_dir.
  3. /shared_inference/$USER/<job id>/perf.csv (or .../model_blog_logs/<job id>/perf.csv), slurm_output/perf_csv/*<job id>*.csv, then ./perf.csv, retried for about 30 s to ride out NFS propagation.

Rows are then copied (or appended without the header) into ./perf.csv so madengine report to-html and the run summary find them. If the source is ./perf.csv nothing is appended, so rows are never duplicated.

Local execution of a self-managed card

If a self-managed launcher reaches ContainerRunner, it runs the script directly on the host (no Docker): bash <script> (or python3 for .py), working directory = the script's directory, model env_vars and context env_vars injected, and only the keys logged, never the values. The script must be a .sh, .slurm or .py file, or a directory containing run.sh.

llm-d deployment

Benchmarks an llm-d stack (vLLM model servers behind a Gateway API Inference Extension InferencePool). The benchmark client is an ordinary single-pod Kubernetes Job, so LlmdDeployment subclasses KubernetesDeployment and reuses ConfigMap bundling, log streaming, result harvesting and the perf.csv path. Managed mode

Leave endpoint_url null. madengine installs three pinned helm releases, waits for readiness, reads the endpoint from the live Gateway, benchmarks, then uninstalls. Requirements, checked in validate():

  • helm on PATH;
  • every llm_d.charts.<name>.version set (shipped as null on purpose, so benchmark numbers are reproducible);
  • llm_d.model.uri, or hf_repo to derive it; model.size when the URI is hf://;
  • the Gateway API CRDs (gateways, httproutes) and an inferencepools CRD in either API group; a GatewayClass named by llm_d.gateway;
  • an existing namespace (never created or deleted), and nodes advertising the GPU resource.

llm_d.model.name is required in both modes. It is the model string sent in requests and recorded in results.

Per-launcher configuration

Common keys under distributed: launcher, nnodes (default: the resolved node count), nproc_per_node (default: resolved GPUs per node), backend (exported as DISTRIBUTED_BACKEND, default nccl), and the rendezvous port as port or master_port (default 29500; port wins on SLURM, master_port on Kubernetes, so set only one). ROCm & GPU utilities

Host-side GPU discovery lives in utils/ (rocm_path_resolver, therock_markers, rocm_tool_manager, nvidia_tool_manager, gpu_tool_factory, gpu_validator, gpu_config, gpu_memory_gate) and is driven by core/context.py. Two independent ROCm roots are resolved: the host's and the container's.

Host root (GPU detection, validation, build)

Resolved once by resolve_host_rocm_path() and handed to the tool managers:

  1. Top-level MAD_ROCM_PATH key in additional_context (a context key, not an env var).
  2. If env MAD_AUTO_ROCM_PATH=0: stop scanning; use env ROCM_PATH, else /opt/rocm.
  3. Auto-detect, first valid root wins:
    1. /opt/rocm
    2. Versioned /opt/rocm-* (sorted)
    3. rocm-sdk path --root (TheRock pip) when rocm-sdk is on PATH
    4. Env ROCM_PATH, ROCM_HOME, HIP_PATH (up to four parent directories are tried)
    5. /usr/local/rocm, ~/rocm, ~/therock
    6. Root inferred from rocminfo, amd-smi, rocm-smi on PATH (<root>/bin/<tool>)
  4. Nothing found: env ROCM_PATH, else /opt/rocm.

A directory counts as a ROCm root if it has TheRock markers (share/therock/therock_manifest.json or dist_info.json), bin/rocminfo, both SMI tools, an SMI tool with .info/version, or .info/version alone.

In-container root (AMD Docker runs)

Resolved per model by finalize_container_rocm_path() at run time; the host path is not mirrored into the container.

  1. docker_env_vars.ROCM_PATH in additional_context (the override key is ROCM_PATH, not MAD_ROCM_PATH).
  2. ROCM_PATH, else ROCM_HOME, from the image's OCI config (docker image inspect).
  3. In-image probe (docker run --rm --entrypoint /bin/sh): rocm-sdk path --root, /opt/rocm, /opt/rocm-*, any other /opt/*, /usr/local/rocm.
  4. /opt/rocm with a warning.

A value from an earlier model in the same run is cleared unless the user supplied it, so every image is resolved afresh. The run-phase table prints host and container ROCm root, install type (apt / therock / unknown) and version side by side.

Behavior

  • Types: CSV values keep native numeric types; cells that look like JSON objects/arrays (configs, multi_results) are parsed into nested documents; NaN becomes null.
  • Metadata: each document gains _meta_uploaded_at (UTC) and, if absent, created_date.
  • Unique key: if not given, the first of model, name, id, timestamp, date, pipeline whose values are unique in the first 100 rows; failing that, model (plus timestamp when present). Upsert matches on those fields with $set. A document missing every key field is silently skipped in upsert mode. --no-upsert uses plain insert instead.
  • Indexes: single-field indexes on the key fields, or on whichever of model, timestamp, date, status, pipeline exist; plus a non-unique compound index when there are several key fields.
  • Exit codes: 0 on success; a partial upload exits 0 if anything was written, else 1; a missing file or total failure exits 1.
  • MONGO_PASSWORD is embedded in the connection URI (mongodb://user:pass@host:port/authSource); use a least-privilege account and keep it out of shell history.

Contributing & code style

Style rules

  • Formatting: Black, line length 88, targets py38–py311.
  • Imports: isort profile = "black", known_first_party = ["madengine"].
  • Lint: flake8 with --max-line-length=88 --extend-ignore=E203,E501,W503.
  • Types: mypy (python 3.8, check_untyped_defs, no_implicit_optional, warn_unreachable, strict_equality); the hook only checks src/madengine/ and excludes scripts/. Type hints are expected on public functions.
  • Security scan: bandit via pre-commit, configured in pyproject.toml (excludes tests; skips B101).
  • Hygiene hooks: trailing whitespace, EOF newline, YAML/JSON/TOML validity, files > 1000 KB, merge-conflict markers, stray debug statements, LF line endings.
  • Docstrings: Google style.
  • Commits: conventional prefixes feat:, fix:, docs:, test:, refactor:, style:, perf:, chore:. Add a CHANGELOG.md entry for user-visible changes.
  • Reviews: .github/CODEOWNERS assigns default owners.

Security rules (as implemented)

  • Quote shell interpolations. shlex.quote() is used wherever user-controlled values (image names, paths, container names, build args, registry hosts) are interpolated into shell strings, across core/docker.py, docker_builder, container_runner, conda_env, slurm, llm_d_stack and the orchestrators. New code that builds a command string must do the same.
  • Registry passwords never reach a command line. login_to_registry() passes the password in the MAD_REGISTRY_PASSWORD environment variable of the subprocess and pipes it to docker login --password-stdin, run with secret=True.
  • Credential files are validated. credential.json must be a JSON object, otherwise loading fails with a ConfigurationError. Blank and shipped-template values (your-docker-username) are treated as unset so a placeholder never overrides a working ambient docker login.
  • Logs and manifests are scrubbed. Console masks MAD_SECRETS*=... assignments and common token shapes (hf_, sk-, ghp_, xox*-) with ***REDACTED***; manifest_safe_context() removes MAD_SECRETS_* values from the context written to build_manifest.json. Log environment keys, never values.
  • Least privilege containers. Ordinary runs do not request CAP_SYS_ADMIN or /dev/fuse. Both are added only for SSHFS-mounted NAS data; user pre-scripts and rocprof/perf tools keep CAP_SYS_ADMIN without /dev/fuse.
  • Kubernetes cleanup is label-scoped. A rerun deletes only objects labelled app=madengine, so a shared namespace is not swept.
